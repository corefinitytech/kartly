# ADR-0003: Auth — Better Auth, argon2id, sessions, and non-blocking email verification

**Status:** Accepted
**Date:** 2026-09-30

## Library choice

Better Auth (v1.7), as fixed in the PRD. It met every requirement: Drizzle adapter with table/field remapping onto our `users`/`sessions`/`accounts` tables plus a new `verifications` table, custom password hash/verify hooks (argon2id), database sessions, cookie configuration, and server-side `auth.api` callable from Next server actions. No fallback to Auth.js v5 was needed.

## Password hashing

argon2id via `@node-rs/argon2` (native binding, Vercel Node runtime compatible): memory 19456 KiB, time cost 2 iterations, parallelism 1 — the OWASP baseline for argon2id. Password policy is 10–128 characters, rejected if in a built-in common-password list or containing the email local part; no composition rules.

## Schema reconciliation

Better Auth expects its own column set; migration 0003 renames/remaps rather than replacing tables: `users` gains `email_verified`, `image`, `updated_at`, drops `password_hash` and `email_verified_at` (the credential hash lives in `accounts.password`, per the library); `sessions` stores the raw token column (the library hashes tokens itself) and `ip_address`, which we overwrite with our salted SHA-256 IP hash in a `session.create` before-hook, so no raw IP is ever stored; `accounts` is reshaped to the library's provider fields; `verifications` holds email/reset tokens (deleted on use or expiry). Our columns (`role`, `status`, `phone_enc`, `locale`, `referral_code`, `age_confirmed_at`) are kept and exposed as read-only additional fields.

## Sessions and CSRF

Database sessions, 30-day sliding expiry (refreshed daily), `kt_`-prefixed HttpOnly + Secure + SameSite=Lax cookies. CSRF: Better Auth's built-in origin checking with `trustedOrigins: [APP_URL]` covers all `/api/auth/*` mutations; our own mutation routes (cart, consent, account actions as server actions) are protected by Next's origin checks for server actions and SameSite=Lax cookies.

## Email verification does not gate sign in or checkout

`requireEmailVerification` is false. Verification only gates features the PRD lists for later milestones (saved payment methods, reviews). Rationale: Resend's free tier without a verified domain only delivers to the account owner's own address, so a reviewer signing up with their own email would never receive a link; blocking sign-in or checkout would break the live demo. Verification/resend/reset emails never fail the flow: send failures are caught, logged without PII, and surfaced as calm messages.

## Rate limiting

The `/api/auth/[...all]` handler applies named policies before the library: sign-in 5/15 min (keyed email + IP), sign-up 5/h per IP, password reset 3/h, verification resend 3/h — all returning the shared error shape with a `Retry-After` header. An in-memory per-email+IP lockout (5 failures / 15 min with backoff messaging) adds timing-safe behaviour on top.
